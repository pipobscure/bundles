0x07II · the primitive
Why this needed the runtime at all

An application is a tree.
Not a blob.

Bundlers collapse JavaScript into one file. An application is an entry point, sibling modules, a package.json, templates, static assets, sometimes a native addon.

# survives a bundler import helper from './helper.js' # does not readFileSync(join(__dirname, 'tmpl/mail.html')) require(`./plugins/${name}`) dlopen('./build/Release/addon.node')

Node's module resolution — and every single fs call — assumes that tree is on a real disk. A bundler rewrites its slice of module loading; everything else keeps pointing at directories that aren't there.

Don't teach the bundler about more file types.

Teach the runtime that a file can be a directory.

Then assets work. Addons work. __dirname works. Dynamic require works. Not because anyone special-cased them — because they all resolve against a tree, and the tree is real.

the reframe07

"Every bundler bug you've ever filed is downstream of this. It rewrote the imports it could see, then some library did a dynamic require, and it fell over at runtime, in production, on a Friday."

This slide converts skeptics — everyone has been burned by exactly this. Let the code block land. Pause after "does not."

This also answers "why did you have to touch Node?" — because the alternative is patching resolution from userland, forever, incompletely.

0x08II · the primitive
Piece 1 · zip support in node:zlib

baseOffset — a zip that
doesn't start at byte zero.

Zip records offsets internally. Seed them with a base offset and the archive stays valid even when it is not at the start of its file.

  • Append it after a shebang line → a self-executing archive.
  • It is still a zip. Every tool you already have still opens it.
  • Read paths enforce size limits and reject malformed records — zip-bomb and corrupt-input guards, with real error codes.

No custom container format. No injection tool. Concatenation.

ZipEntry · ZipFile · ZipBuffer · createZipArchive()08

"This is the least glamorous slide in the deck, and it's the one that makes everything else possible."

Hammer "still a valid zip." It is not a bespoke container that happens to resemble one. That's what makes unzip app.run work in the demo — and inspectability is a genuine property, not a party trick. It's also the thing jar got right and everybody since keeps re-deriving.

If asked why this had to be in core rather than userland: because the loader needs to read it during bootstrap, before userland exists.

0x09II · the primitive
Piece 2 · mount and load

Resolve the program
against the archive.

$ node --experimental-vfs \ --vfs-mount app.zip \ --vfs-load
  • --vfs-mount mounts a source. The provider comes from the source, not the name: a directory gets RealFSProvider, zip bytes get ZipProvider.
  • --vfs-load runs the entry point out of the first mount — --vfs-load=n picks another — resolving it and every later require / import against it. The archive's own package.json "main" decides what runs.
  • Resolution primitives were rerouted through a VFS-aware path that defers to the real bindings when nothing is mounted — so unmounted behaviour is unchanged.
And then the good bit

--vfs-load takes the entry point from the mount, never from a positional. So a trailing --vfs-mount with no value takes whatever the kernel appends —

#!/usr/bin/env -S node \ --experimental-vfs --vfs-load --vfs-mount

— which is the script's own path. The file mounts itself and runs its own embedded main.

argv[1] is the source's real path, so the file can still read its own bytes — which is how a launcher verifies itself. Worker threads inherit the mounts.

node:vfs foundation by Matteo Collina09

Get the credit right here, out loud. node:vfs — the subsystem itself, MemoryProvider, RealFSProvider — is Matteo Collina's, and so is the VFS module loading that makes a mount resolvable. Yours is the zip support in node:zlib, the Zip VFS provider, and these two flags. The status slide breaks it down; don't blur it here.

"The shebang thing is my favourite accident. The kernel appends the script's path to the interpreter line. If the last flag is a --vfs-mount still waiting for a value… it gets the script itself."

One honest footnote, if anyone is taking notes: this exact form is not what the tool actually ships as a prefix. The kernel appends the path and then the user's arguments, which leaves nowhere to write the -- that stops node claiming them — so app.run --help prints node's help. The shipped prefix is two lines of sh that exec node with "$0" and a --, and slide 0x0F shows it. The trick on this slide is real and is a property of the flag; it is just not sufficient on its own.

Two details worth having ready. The mount point is node's to choose, not yours — mounts live in a reserved namespace, so one can never shadow a real path. And because the provider is picked from the source's bytes rather than its name, a signed archive can be called app.run, bundle.zip or nothing in particular and still mount the same way — which matters in Act III, where renaming a file must not change what checks it.

Neither flag takes orders from the environment. --vfs-load is refused in NODE_OPTIONS outright — which entry point runs is the command line's decision, and NODE_OPTIONS is parsed first, so otherwise an environment variable could redirect any invocation on the machine. --vfs-mount is allowed there, but those mounts sort after the command line's, so the index still counts the mounts you asked for.

Why two flags? Because you may want several mounts and exactly one entry point. Mounting and running are different concerns. Expect this question.

If someone asks about native addons — and at a Node conference someone will — they are a separate pull request (65680), because dlopen opens a shared object by path and a VFS path has no inode to open. It reads the addon out of the mount and loads it from a private, self-cleaning image: an anonymous memfd on Linux, so the bytes never touch the disk at all, an unlinked temp file elsewhere. Until it lands, a bundle containing a .node file mounts and then fails at require. The status slide has it as its own row.

Note what's absent from this slide: any mention of trust. Mounting an archive is just mounting an archive. Node will happily run an unsigned one, and that's correct behaviour.

0x0AII · the primitive
Piece 3 · the extension point

registerProvider() — you
decide what backs a mount.

vfs.registerProvider({ name, canHandle(resolvedPath, stats), create(resolvedPath, stats) });
  • Registered providers are consulted before the built-ins — RealFSProvider and ZipProvider are just the last two entries.
  • Selection happens after preload modules have run. So a -r module can install a provider for the source that is about to be mounted.
  • Yours sees every source — directories included — and outranks the built-ins, so it can wrap or vet, not just add formats.
This is the whole trick

Node ships a hole, not a policy. It says: here is where a decision could go, and it is none of my business what you put there.

Be exact about the ordering — preloads run during bootstrap; provider selection happens after. That gap is the extension point.

Careful with your verbs from here on. Node does not refuse anything. Node does not enforce anything. A provider you chose to install can decline to return a filesystem. If you don't install it, your archive runs. That's not a weakness in the design — it's the design.

0x0BII · the primitive
One of the design decisions

Node defines no signature
format. On purpose.

Bake a signature format into the runtime and you have promised to be right about cryptography forever, on the release cadence of a runtime.

  • You get stuck. Node 26's blessed format is still Node 26's blessed format in 2032.
  • There is no single right trust model. An internal CA, Sigstore and OIDC, pinned keys in an air-gapped site — all legitimate, all different.
  • One blessed format crowds out the rest. Whatever ships in core wins by default, however wrong it turns out to be.

Leave the hole, and upgrading your signature scheme is a dependency bump — not an OS release, not a Node major, not a five-year deprecation.

why the format stays in userland

One design decision, argued properly — not the thesis of the talk. It earns its ~85 seconds because the evidence is good, but don't oversell it: it is one of several choices, and the talk does not stand or fall on it.

"Android is the natural experiment. They took jar signing — a 1996 design — put it in the platform, and then spent fifteen years discovering what was wrong with it. Every fix was an OS release. Every device that couldn't update, didn't get it."

Get the facts right, they're checkable: v1 is jar signing, which signs per-entry digests listed in a manifest rather than the archive itself. Janus (CVE-2017-13156, 2017) exploited exactly that gap. v2 arrived in Android 7 with a whole-file hash; v3 in Android 9 added key rotation; v4 in Android 11 added streaming install. The jar scheme has its own version of this — entries added after signing leave a jar "partially signed" rather than invalid.

The move to make explicitly: "I am building a signing scheme in this talk. I think it's a decent one. I would not want it in Node — because in three years I'll have learned why it's wrong, and I'd like to be able to fix it."

That self-implicating turn is what keeps this from sounding like an excuse for unfinished work.

One policy, entirely in userland

So here's the scheme
I happen to like.

Learned from jar

The central directory is inside the hash, so the member list is signed. You can't add an entry.

Learned from apk v2

Whole-file, not per-entry. There is no gap between structures to hide in.

Four states, not two

unsigned invalid untrusted valid

a library. not a standard. replaceable.0C

"Everything from here down is optional. None of it is in Node. If you delete all of it, your archive still runs — you just don't know who made it."

Where the signature lives is the neat bit: it has to be inside the file, but can't be covered by its own hash. Zip hands you that — the EOCD comment is the last structure, so you hash everything up to it.

The three cards are the payoff for slide 0x05. This scheme is prior art plus its post-mortems: jar's mistake was signing a list of entries rather than the archive; apk v2's fix was whole-file. Say that you copied their homework and their corrections.

The four states, briefly — the interesting one is "valid but untrusted": genuinely signed, bytes intact, and you have no idea who this person is. That's a different problem from tampering, and conflating them is how you train people to click through warnings.

Beat 2 — build (20s). Fast. --launcher is worth half a sentence: it prepends the shell prefix the package ships, so nobody has to know it lives in node_modules. --prefix <file> is still there for your own launcher, or for a node binary.

Beat 4 — run it (25s). "Twenty-one kilobytes, and it is a program."

Fallback: artifacts are committed — just ./app.run help and move on. Do not debug on stage.

Demo 02 · 03

Sign it. Break it.
Then opt in to caring.

# signed via sigstore — identity, not a key file $ npx bundle verify app.run VALID — signature good, certificate trusted identity: github.com/pipobscure/… (GitHub Actions)

That last one is not a bug. Node was asked to run a zip, so it ran a zip. Caring is something you switch on.

# now install a provider that has an opinion $ node --experimental-vfs -r @pipobscure/bundle/register \ --vfs-load --vfs-mount app.run Error [ERR_BUNDLE_UNTRUSTED]: archive failed verification at BundleProvider.open (…/provider.js)

0x11III · the optional layer
Demo 05

Provenance says who.
Now ask what.

A bundle is a closed set. Nothing resolves later; nothing is fetched at install. That is the shape a review can actually be complete over.

So the review is a step, not an afterthought — and it sits before the signature, because a signature is a claim about bytes you stand behind.

$ npx bundle audit --check app.bundle \ && npx bundle sign --launcher … error: app.bundle has not been audited

The verdict names the archive's sha256, so rebuilding invalidates it. Otherwise the gate approves any later build on the strength of one earlier approval — which is every “review completed” checkbox ever.

observe → create → audit → sign11

The skill exists (skills/audit-bundle/) and the gate is a shipped command (bundle audit --check), so this is a live demo rather than a promise. Plant something findable first — see below. If you are running long, show the refusal and skip the review itself; the refusal is the point.

"Every attack on the timeline earlier was legitimately signed by a legitimately compromised account. Provenance would have told you it came from the real maintainer — and been completely useless. You need both halves."

The move to make here is that this used to be the last demo — a thing you could do to an archive somebody sent you. It is now step three of four, because the same argument applies pointing inward: if you would not run someone else's bundle without reading it, don't sign your own without reading it either. Same skill, same checklist, run at both ends.

The strong framing: this is why the trust layer being optional and pluggable matters. Signature checking is one policy. "Extract it and read it" is another. "Diff it against the last release" is a third. Same hole, different things plugged into it.

On the diff: in the release pipeline the baseline is the currently published bundle, verified before use — because a diff makes everything the baseline already contained read as "unchanged" and therefore go unread. Worth one sentence if someone asks why not just review the source tree: what ships is the archive, and whether the set is right isn't visible until the bundle exists.

If demoing live: plant something obvious in the tree (an env read plus an outbound POST) so there's something to find.

Demo 06

The tool ships as
a bundle of itself.

# package.json — the whole bin entry "bin": { "bundle": "./bundle.run" } # so npm links the artifact itself $ ls -l node_modules/.bin/bundle bundle -> ../@pipobscure/bundle/bundle.run $ head -c 89 node_modules/.bin/bundle #!/bin/sh exec node … --vfs-mount "$0" -- "$@"

No wrapper script. 677 members, sigstore included — the dependency tree stops being something you fetch and becomes a fixed set /audit-bundle can read in full.

If the model doesn't hold for this tool, it doesn't hold for anything. So it doesn't get an exemption.

# version N verifies version N+1 $ bundle verify \ --identity '…/release.yml@refs/heads/main' \ --issuer 'token.actions.githubusercontent.com' \ bundle.run

Pinned to the release workflow, not to me. Running it doesn't check it — a #! carries no preload. Checking is a separate act, with a copy you already trust.

no lock file. there is no install.

This is the dog-food slide, and as of this build it is true rather than aspirational. It used to be a prepared Q&A answer that ended "it isn't built yet". It is built: npm run manifest:cli → pack:cli → audit → sign:cli, and the published package carries the result.

"Everything I've asked you to do to somebody else's artifact, this tool does to itself. It arrives as one signed file. The command you run is a launcher that verifies that file, mounts it, and re-hashes every member as it reads it. There is no install step to compromise, because there is no install step."

If someone asks about the lock file — and they will — the answer is on the kicker. A lock file pins the bytes of a tree that is still fetched and executed at install time. A signed bundle removes the step rather than pinning it. "The same bytes" stops being a claim about versions and becomes literally the same bytes. The lock file stays useful for contributors reproducing a build; that's a different question.

There is no launcher, and that is the interesting bit. An earlier version put a small JS shim in front that verified the archive before mounting it. It got deleted: the shim was unsigned code installed beside the thing it vouched for, so anyone who could swap the archive could swap the shim — it detected corruption, not an adversary — and it put an opaque step in front of the one file you want people reading. bin now points straight at the artifact.

Say the honest half out loud: running it does not verify it. Checking is a separate act with a copy you already trust — bundle verify bundle.run, or bundle run bundle.run to execute it through the verifying mount. Same opt-in story as slide 0x10, applied to the tool itself.

Cut this slide first if you are running long. It is the most satisfying beat in Act III and the least load-bearing — the argument survives without it.

0x13IV · close
Before anyone else says it

What this is not.

VFS is not a sandbox

It redirects fs calls whose resolved path falls under a mount. It does not confine untrusted code. Node's own docs say so.

Verification is not confinement

A checked mount proves the code is what someone you trust signed. Once it runs it has the full authority of the process. Provenance, not privilege.

The check is opt-in — by design

Drop the -r and the archive mounts unverified. That is not a hole to close; it is the consequence of Node not owning your trust policy.

My scheme will age badly

So will yours. That's the whole argument for keeping it out of core, and I'd be a hypocrite to pretend otherwise.

And it is experimental: a flag, an API that can still move, and a userland package at version zero.

honest limitations13

Do not skip this even if you're over. Cut demo 4 instead. Naming your own limits before the audience does is the highest-return thing in the last three minutes.

The third card is the one to dwell on, because it's the question a security person will ask, and the answer is the design rather than an apology: yes, someone can skip the check. If that's unacceptable in your environment, that's your build pipeline's job, or your OS's — not the language runtime's.

"If you take one caveat away: this is provenance, not privilege. It tells you the code is what someone you trust signed. It does nothing about what that code does next."

thank you15

Prepared answers:

  • "Shouldn't Node just verify signatures?" — the question the talk exists to answer. Point at Android: four schemes, four OS releases. Then: whose CA? which algorithm? what happens on failure? Every answer is somebody's wrong answer.
  • "Then what stops me shipping an unsigned archive?" Nothing, and nothing should. Your CI, your registry, your deployment tooling are where that belongs — all of which can use the same library.
  • "Isn't this just a .jar?" Same shape, deliberately. Differences: jar signs a manifest of per-entry digests, so entries can be added after signing and the archive structure isn't covered — this hashes the whole file including the central directory. And the JVM verifies jars; here nothing verifies unless you ask it to.
  • "Why not containers?" Different granularity. A container ships an OS to run one CLI. This is one file on the machine you're already on — and inspectable with unzip on a locked-down laptop.
  • "npm has provenance attestations now." Yes, and they're good, and they're a neighbouring problem: provenance for packages you're about to install. This is the artifact you already built. Sigstore is the common substrate; they compose.
  • "How do I get the tool, and why would I trust it?" Covered on 0x12 — point back at it rather than re-explaining. It ships as a signed bundle of itself, verified by the copy you already have, pinned to the release workflow's identity rather than to mine. The two honest caveats: the first copy is trust-on-first-use however you dress it up (mitigated by it being TOFU over an artifact you can read completely), and the launcher verifying the signed CLI with the unsigned code beside it is circular — it catches a substituted archive, not a compromised install. HISTORY.md, implementation notes §3.
  • "Reproducible builds?" Orthogonal and worth having. This says the bytes are signed by a known identity; it doesn't say those bytes correspond to that source.
  • "Sigstore certs only live ten minutes — how does verification work later?" Solved, and worth a sentence because it is a nice bit of design. The signature is checked against the certificate's validity at signing time, so the archive carries the evidence of when that was: a full sigstore bundle — Rekor entry and RFC 3161 timestamps — in the EOCD comment beside the signature. It has to live outside the hash, because it is produced after the signature exists; that is the same placement RFC 3161 gives timestamp tokens in CMS unsignedAttrs.
  • "What about no Node on the target?" The same archive rides on a Node SEA — bundle sea — and that one does verify itself before running, because the container carries its own bootstrap rather than relying on a preload the kernel won't give it. ~155 MB, which is the honest floor for zero-dependency distribution. One sentence unless they push; it is a different talk.
  • "Windows?" Be straight: the shebang route is POSIX. Mounting a plain archive is the portable answer. Check the current state before you present rather than guessing on stage.
