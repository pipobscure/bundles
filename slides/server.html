🌳 JavaScript · deploying · sharing tools

Ship the Tree

A story about shipping JavaScript.

Philipp Dunkel · @pipobscure.com

github.com/pipobscure/bundles

Open with the question, not the tool. Everyone in this room has deployed something and later wondered what was really running on that box. This talk is a story in four parts: the server, the tools we share, what had to exist before any of this could work, and what you can do now. The tool is called bundle, it is open source, and it is experimental: it needs Node 26.11 and a flag. Say that now so nobody feels tricked at the end.

I · On the server

We patched around it

Lockfiles

Pin which versions. The network and the install scripts are still in the deploy.

Container images

Same bytes everywhere. You ship an operating system, and npm ci still ran inside it.

Bundlers

One JS file, until templates, native addons or a dynamic require fall out of it.

Compiled binaries

One file, but you can’t look inside, and it is rarely signed over the whole thing.

All of them work. None tells you, months later, exactly what runs and who put it there.

Don't trash any of these; the room uses all four and they all work. Lockfiles fixed which versions you get. Containers fixed "same bytes everywhere", at the cost of shipping an OS to run one service. Bundlers like esbuild or ncc collapse the JavaScript but leak everything that isn't an import. pkg, bun build --compile and Node SEA give you one file, but it's opaque. Land the last line: none of them answers the question from the previous slide.

III · What had to exist first

Apps are trees

// survives a bundler
import helper from './helper.js'

// does not
readFileSync(join(__dirname, 'mail.html'))
require(`./plugins/${name}`)
process.dlopen(m, './addon.node')

Module resolution and every fs call assume the tree is on a real disk.

So teach the runtime that a file can be a directory.

Now the mildly technical part: what had to exist before any of the wish list was possible. Every bundler bug you've filed is downstream of this. The bundler rewrote the imports it could see; then a library read a template next to itself, or did a dynamic require, and it fell over in production. Instead of teaching the bundler more file types, teach Node that one file can be the directory the app runs in. Then __dirname, assets, addons and dynamic require all just work, because nobody special-cased them.

III · What had to exist first

Archives, built in

v26.8

ZIP in node:zlib

Read, write and stream ZIP archives, built into Node.

why

A format every tool already opens. It still reads with a launcher in front of it, and malformed or oversized archives are refused.

import { ZipEntry, createZipArchiveSync } from 'node:zlib';
const zip = createZipArchiveSync([
  ZipEntry.createSync('package.json',
    Buffer.from('{"main":"index.js"}')),
  ZipEntry.createSync('index.js',
    Buffer.from('console.log("hi")')),
]);
writeFileSync('app.zip', Buffer.concat([...zip]));

$ unzip -Z1 app.zip
package.json
index.js

ZIP support in node:zlib: ZipEntry, ZipFile, ZipBuffer and createZipArchive. The code on the right is real and runs on a stock Node 26: two entries, an archive, written to app.zip. Why ZIP: it's the format everyone's tools already open, so unzip lists it, with no special tooling. Two details make the single-file trick work: an archive can sit behind other bytes, like a #! launcher, and still read correctly; and it refuses malformed records and zip bombs. ZIP is easy to get subtly wrong, which is why it went through a long review with security researchers. Keep app.zip in mind; it comes back two slides from now.

III · What had to exist first

Files from anywhere

v26.4 · by Matteo Collina

node:vfs

An fs-shaped file system whose files come from a pluggable provider, mounted at a path.

why

Every fs call under the mount goes to the provider, so code that reads files keeps working, unchanged. A ZipProvider (v26.9) mounts an archive.

import * as vfs from 'node:vfs';

const mem = new vfs.MemoryProvider();
mem.writeFileSync('/hello.txt', 'hi from memory');
const root = vfs.create(mem).mount(); // /dev/null/vfs/1

readFileSync(`${root}/hello.txt`, 'utf8');
// 'hi from memory'

node:vfs is Matteo Collina's work: an fs-shaped API backed by a provider, memory, a real directory, or anything else, mounted at a path Node picks. Walk the code: a file written into a MemoryProvider, the provider mounted, and then plain readFileSync, the ordinary node:fs, reads it back from the mount point. That's the point: code that reads files doesn't change at all. The ZipProvider (v26.9) is the bridge between the two slides: it is a provider whose files come from an archive, so a zip mounts as a directory.

III · What had to exist first

Importing from a zip

v26.10 · addons v26.9

Loading from a mount

require, import, package.json lookup and format sniffing all resolve inside the mount.

why

__dirname, assets and dynamic requires just work. Worker threads see the same mount, and native addons load from it too.

import * as vfs from 'node:vfs';
import { ZipFile } from 'node:zlib';

const zip = await ZipFile.open('app.zip');
const root = vfs.create(new vfs.ZipProvider(zip)).mount();

await import(`${root}/index.js`);
// hi

The third piece: module loading that knows about mounts. Same app.zip as two slides ago, mounted with the ZipProvider, and then a plain dynamic import of its index.js, which prints hi. Under the hood, four module-resolution primitives (reading package.json, finding the nearest scope, legacy main resolution, and sniffing whether an extensionless file is ESM) go through a VFS-aware path, so require and import resolve inside the mount, and behave exactly as before when nothing is mounted. That's why __dirname, templates next to the code, and dynamic requires work without a bundler rewriting anything. Worker threads inherit the mount, so code can't spawn a worker that escapes it. Native addons were their own change: dlopen needs a real path, so the addon's bytes are loaded from a private image, an anonymous memfd on Linux.

III · What had to exist first

One flag at startup

v26.10

--vfs-load

Mounts a directory or an archive where Node chooses, and runs its package.json main.

why

One flag, so a two-line #! launcher makes a zip a program. Refused in NODE_OPTIONS: the environment can’t redirect what runs.

$ node --experimental-vfs --vfs-load=app.zip
hi

$ NODE_OPTIONS="--vfs-load=app.zip" node
node: --vfs-load= is not allowed in NODE_OPTIONS

The fourth piece, and the one that makes it a program: --vfs-load. All of the last slide in one flag: it mounts a directory or a zip, chosen by its content rather than its name, at a mount point Node picks so it never shadows a real path, and runs the package.json main. Again the same app.zip, again hi. The second command is the safety rail: --vfs-load is refused in NODE_OPTIONS, because which program runs is the command line's decision, and the environment must not be able to redirect every node on the machine. And because the flag names its source, a two-line shell launcher in front of the zip can pass the file's own path: that's how a .nzip runs by name, which we'll see in part four.

III · What had to exist first

All shipped in Node

v26.4

node:vfs

A file system with pluggable providers. By Matteo Collina.

v26.8

ZIP in node:zlib

Read and write archives, reviewed with security researchers.

v26.9

ZipProvider

Mount an archive as a directory. Native addons load from it.

v26.10

--vfs-load

Run a program straight out of the archive.

Stock Node from nodejs.org, behind --experimental-vfs. No fork, no patches.

Before 26.10, running this meant a patched Node, built from source on every server: 30 to 90 minutes. Now it’s the download.

The summary: we shipped it. Point back at the last two slides; these are the same four pieces, all upstream and all released. node:vfs is Matteo Collina's work, and it's the foundation. On top of it: ZIP support in node:zlib (nodejs/node#64339), which went through a long review with security researchers, because ZIP is easy to get subtly wrong and every mistake is a security hole. Then the ZipProvider (#64915) and native addons from a mount (#65680). Then --vfs-load (#65748), the keystone: node --vfs-load=app.nzip runs the app inside. The bottom line is why upstream mattered in practice: before 26.10, deploying this way meant a 30 to 90 minute source build of a patched Node on each server.

III · What had to exist first

Userland: bundle

🌳 bundle

npm: @pipobscure/bundle · a CLI and an API

record

Run the app once, and write down every file it reads.

create

Archive exactly those, with a launcher in front.

sign · attest

Say who built it, and let others say what they found.

install · update

Onto your PATH, and kept current.

publish · search

Names in your own Atmosphere account.

suites · plugins

Toolsets, and apps that take plugins.

Node mounts the tree and runs it.

node:vfs · zip · --vfs-load

Node gives us the primitive: a tree in one file, mounted and run. Everything people actually do with such a file lives in userland, in one ordinary npm package, @pipobscure/bundle, with a CLI and an API that does everything the CLI does. Walk the six briefly; each gets its own slide later, so don't explain them here. record runs the app once and writes down every file it opens, which beats static analysis. create builds the archive, with a two-line launcher in front so it runs by name. sign and attest say who built it, and let others say what they found. install and update get it onto your PATH and keep it current. publish and search give it a name in your own Atmosphere account. suites and plugins cover toolsets and apps that take plugins. Why not in Node: this part has to move fast and stay replaceable, and the runtime should stay small. And the bundle command is itself shipped as a bundle.

III · What had to exist first

Keyless signing

1 · observe

Run the app once and write down every file it reads.

2 · create

Archive exactly those files. Same files, same bytes.

3 · audit

Review it against the last release: you, or Claude in CI.

4 · sign

Only if the review came back clean.

# release.yml
permissions:
  id-token: write # that’s the key

Sigstore signs as your CI workflow, or as your browser sign-in on a laptop.

Users can require exactly that workflow, on main.

The second prerequisite: signing that doesn't mean managing keys. Sigstore issues a short-lived certificate for an identity you already have: your GitHub Actions workflow in CI, a browser login on your laptop. Nothing to store, nothing to leak. And signing is its own step, after an audit: observe, create, audit, sign. Recording beats static analysis because it catches dynamic requires and data files; the unused module in your source simply isn't in the archive. Archives are reproducible: the same files make the same bytes. bundle's own releases go through exactly this, with the audit done by Claude against the previous release.

III · What had to exist first

No new registry

publisher

Listing

“mdview is at this URL.” Releases stay where they are.

curator

Suite

“These go together, and each must carry this.”

auditor · scanner · IT

Attestation

“Audited”, “permitted”, “malware”, about one file’s hash.

Each one is a record in their own Atmosphere account, any provider.

Checked against the owner’s key with nothing but node:crypto.

You hold the policy: whose word counts, and whose warning stops an install.

An open index only says whom to ask.

The third prerequisite, and the one people don't expect: accounts that already exist. If you have an Atmosphere account, from whichever provider, you already have a place to publish signed records that anyone can verify without trusting the server. Every role writes only to its own account: the publisher says where the file is, the curator says what goes together, the auditor or scanner or your IT department says what they think of a file. A backlink index (Constellation) helps find records, but every record is fetched from its owner and checked against their key. Nobody runs a registry, so there's nothing in the middle to compromise. You don't need an account to install; only to publish names or attestations.

IV · What you can do now

Your app, one file

$ bundle create --base ./app -f app.manifest --launcher -o greet.unsigned.nzip
* unsigned archive (3 members, sha256 digests)
$ bundle sign greet.unsigned.nzip
* wrote greet.nzip (1904 bytes)
$ ./greet.nzip Grace
hello, Grace
$ head -2 greet.nzip
#!/bin/sh
exec node --no-warnings --experimental-vfs --vfs-load="$0" -- "$@"

Two kilobytes

Only the files the app read.

It’s a zip

unzip -l shows everything in it.

Plain node runs it

No node_modules, no install step.

Demo, or show the slide if the network is bad. The app was recorded first (the observe step), so the archive holds exactly the three files it read, and the unused module in the source isn't there. --launcher puts a two-line shell script in front of the zip, so the file runs by name. The signature covers the whole file, launcher included. That's wishes one and two from the list: one file, decided at release, runs by name. On Windows, bundle install sets up a .nzip file association so the same file runs by name there too.

IV · What you can do now

See who vouches

$ bundle install @alice.example/tool
* tool: sha256:3f1a… (signed)
   1 signed by   …/acme/tool/.github/workflows/release.yml@refs/heads/main — new
   2 attested by audit.acme.com as audited — trusted by policy
     WARNING     scanner.example as malware — marked it bad
* accept which? numbers (1,2), 'all', or Enter to decline:

Nothing runs to install

Fetch, check, move into place. No install scripts.

You decide once

Your answer is remembered for every update.

Name it any way

A URL, a domain, or a name someone published.

Think of it as curl-pipe-sh with the two scary parts removed: nothing runs to install it, and nothing lands on disk unless it checks out. A file that doesn't match its signature is refused outright, so a tampered download never lands. Walk the prompt: a signer you haven't seen before is a question; an auditor your policy trusts goes straight through; a warning from a stranger is shown, not obeyed, because anyone can publish one, while a warning from someone you listed refuses it outright. Three ways to name an app: a URL, a domain whose TXT record says where, or a published name like this one. Next slide: the same install, without a terminal.

IV · What you can do now

One click installs

on your page, README or post

<a href="nzip:alice.example/devtools">
  Install devtools
</a>

🌳 Install devtools

→

bundle opens a window with the same review and the same questions.

No terminal needed

Once bundle is installed, the browser hands nzip: links to it.

Names, never downloads

A link names something published. A page can’t point bundle at any old file.

Apps, suites, plugins

A plugin’s link installs it into its app. publish prints the link.

This is the one people underestimate. Once bundle is installed, it registers itself for nzip: links on Linux, macOS and Windows. An author puts a link on their page, their README, or in a chat message or a post; clicking it, the browser asks whether to open bundle, and bundle runs the same install as the terminal command, with the decisions in a window. So your designer, your PM, or the colleague who never opens a terminal can install your team's tools, and they still see who vouches for them. Safety: a link only ever names something published, an @handle/name or an at:// address, never a URL or a domain, so a web page can't make bundle fetch an arbitrary file. What it names is fetched, checked and reviewed like any install. bundle publish and bundle suite publish print the link for you, and the project's page lists every published app with its link. If links ever stop opening bundle, bundle links puts it right.

IV · Back on the server

Deploying now

# /etc/bundle/policy.json
{ "require": { "attesters":
  ["published@did:plc:…"] } }

$ bundle install --system \
    --name example-shop \
    @you.example/shop

# each systemd unit:
example-shop run checkout

One app, every service a part

API, auth, workers, mail… each pinned by hash.

CI vouches for one hash

The servers only accept what that account attested.

Unchanged means untouched

Same bytes, same hash: not fetched, not restarted.

All or none

No half the services on last week’s release.

What’s on the server? One hash, and who vouched for it.

This closes the loop from the first slide. Picture a product made of many services. CI builds each service as a part, builds one app that pins every part's hash, and attests that one hash from its own Atmosphere account. The servers' policy only accepts that attestation, and it names a DID, never a handle, because handles change hands. Installed by name, the app is a command on the PATH, launcher included, so each systemd unit just runs example-shop run checkout: stock Node runs the app, which runs that one part. No unit points at a service's own archive. Archive members all carry a fixed date, so an unchanged part is the same bytes in the next release, keeps its hash, and its service isn't even restarted. Compare that with the deploy on slide two: no registry, no npm install, no copying files around, and a single answer to "what's running".

V · Honestly

What this isn’t

Not stable

Node 26.11+ with --experimental-vfs. Both sides are experimental.

Not proof of safety

A signature says who built it. Review and attestations say the rest.

Not a replacement for npm

You still develop with npm. This changes what you hand over.

Before anyone goes and uses this for everything: three things it isn't. Being upfront here is what makes the rest credible. On "not proof of safety": most npm compromises shipped perfectly signed packages from real, hijacked accounts, which is exactly why attestations from other people exist.
