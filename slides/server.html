🌳 JavaScript · deploying · sharing tools

What’s on
the server?

A story about shipping JavaScript, and how one signed file changes what you can promise.

Philipp Dunkel · @pipobscure.com

github.com/pipobscure/bundles

Open with the question, not the tool. Everyone in this room has deployed something and later wondered what was really running on that box. This talk is a story in four parts: the server, the tools we share, what had to exist before any of this could work, and what you can do now. The tool is called bundle, it is open source, and it is experimental: it needs Node 26.11 and a flag. Say that now so nobody feels tricked at the end.

I · On the server

Deploy day reaches for the internet.

# deploying, 16:40 on a Tuesday
$ git pull && npm install --production
npm ERR! fetch failed registry.npmjs.org/…
npm ERR! 503 Service Unavailable

# the code hadn’t changed.
# the build had.

Someone else’s uptime

The registry sits in the path of every deploy, and you don’t run it.

A dice roll when it’s up

^1.2.0 means “whatever the registry says today”.

Start where most of us started: a web service, and a deploy that runs npm install on the server. The loud failure is the registry being down. npm's own status page has logged an incident roughly every three weeks in recent years (re-check the figure with slides/tools/refresh-chart.mjs before presenting). But the real lesson is quieter: even when the registry is up, resolving at deploy time can give you a different tree than an hour ago. The code you deploy didn't change. The build did. Concede the obvious objection: lockfiles fixed which versions. They didn't take the network out of the deploy.

I · On the server

You shipped a version.
The server got whatever resolved.

$ npm install
added 214 packages in 9s

# which 214?
# from where?
# and what just ran?

Decided at install time

Not when you released, and not when you tested.

Installing runs code

postinstall scripts run before anyone has looked at anything.

Nothing writes it down

Two installs of one version can differ, and nobody can say how.

"When you publish version 1.4, you think you shipped 1.4. What you actually shipped is a recipe, and the server cooks it." The 214 packages line always gets a laugh, because everyone has seen it. Three things: it's decided late, it runs code while deciding, and nothing records what happened.

I · On the server

Knowing the version isn’t knowing the code.

2018

event-stream

A helpful new maintainer, then a wallet stealer in a dependency.

2021

ua-parser-js

An account taken over. Millions of weekly installs shipped a miner.

2024

xz-utils

Years of patient social engineering, for one backdoor.

2025

Shai-Hulud

A worm: it steals CI tokens and publishes itself onward.

Each was published correctly. You asked for a version, you got that version, and you still got owned.

Six months after that deploy, someone asks: what exactly is running on that box? Walk the arc, don't read the list: an accident-shaped trust problem, then targeted theft, account takeover, patient infiltration, and finally a worm that spreads by itself. xz isn't npm, which is the point: this is how software gets attacked now. For Shai-Hulud, the safe framing is "hundreds of packages across two waves in late 2025, and CISA issued an advisory"; don't quote a precise count from the stage. The punchline: version numbers didn't help, because every one of these was a correctly published version.

I · On the server

So we patched around it.

Lockfiles

Pin which versions. The network and the install scripts are still in the deploy.

Container images

Same bytes everywhere. You ship an operating system, and npm ci still ran inside it.

Bundlers

One JS file, until templates, native addons or a dynamic require fall out of it.

Compiled binaries

One file, but you can’t look inside, and it is rarely signed over the whole thing.

All of them work. None tells you, months later, exactly what runs and who put it there.

Don't trash any of these; the room uses all four and they all work. Lockfiles fixed which versions you get. Containers fixed "same bytes everywhere", at the cost of shipping an OS to run one service. Bundlers like esbuild or ncc collapse the JavaScript but leak everything that isn't an import. pkg, bun build --compile and Node SEA give you one file, but it's opaque. Land the last line: none of them answers the question from the previous slide.

II · Sharing tools

Then you write a tool for your team.

how it usually goes

$ git clone … && cd tool
$ nvm use 20  # works on 18?
$ npm ci     # hundreds of MB
$ npm link   # on PATH. somewhere.

how it should go

$ curl -O …/tool
$ ./tool

# that’s it

A CLI is one file, or it’s a support ticket.

The second half of the story. The web service is under control-ish, and now you build tooling: a deploy helper, a code generator, a linter config, something the whole team uses. Getting it onto ten laptops means shipping an install procedure, and then supporting it. "The single best usability improvement I ever made to an internal tool was deleting its installation instructions."

II · Sharing tools

Ten laptops, ten slightly different tools.

“Works for me.”

Which version does your colleague have? Does CI run the one you run?

Updates by Slack message

“Please pull and re-link.” Half the team does.

A toolset, not a tool

Five CLIs that only work together at matching versions.

Someone else’s tool

npm i -g from a stranger runs their install scripts as you.

Same problem as the server, just multiplied by every laptop, and with no ops team watching. Consistency is the theme: the same tool, at the same version, on every machine and in CI, and a way to move everyone forward together. And then the stranger's tool: installing it globally runs their code before you've looked at it.

II · The wish list

What we actually wanted, on the server and on every laptop

1

One file, decided when you release

2

Runs by name, with no install step

3

Says who built it, and can’t change afterwards

4

Others can vouch for it, or warn you off

5

Updates follow the publisher, and bad news finds you

6

The same thing in CI, on laptops and on servers

The pivot of the talk. Read these slowly; everything after this slide delivers one of them. Don't ship the recipe, ship the meal: one file, frozen when you release it, signed, and run as it is. Then let other people say things about that file, and let updates and warnings travel to whoever installed it.

III · What had to exist first

An app is a tree, not a blob.

// survives a bundler
import helper from './helper.js'

// does not
readFileSync(join(__dirname, 'mail.html'))
require(`./plugins/${name}`)
process.dlopen(m, './addon.node')

Module resolution and every fs call assume the tree is on a real disk.

So teach the runtime that a file can be a directory.

Now the mildly technical part: what had to exist before any of the wish list was possible. Every bundler bug you've filed is downstream of this. The bundler rewrote the imports it could see; then a library read a template next to itself, or did a dynamic require, and it fell over in production. Instead of teaching the bundler more file types, teach Node that one file can be the directory the app runs in. Then __dirname, assets, addons and dynamic require all just work, because nobody special-cased them.

III · What had to exist first

What landed in Node, piece by piece

v26.4

node:vfs

A file system with pluggable providers. By Matteo Collina.

v26.8

ZIP in node:zlib

Read and write archives, reviewed with security researchers.

v26.9

ZipProvider

Mount an archive as a directory. Native addons load from it.

v26.10

--vfs-load

Run a program straight out of the archive.

Stock Node from nodejs.org, behind --experimental-vfs. No fork, no patches.

Before 26.10, running this meant a patched Node, built from source on every server: 30 to 90 minutes. Now it’s the download.

Four pieces, all upstream and all released. node:vfs is Matteo Collina's work, and it's the foundation. On top of it: ZIP support in node:zlib (nodejs/node#64339), which went through a long review with security researchers, because ZIP is easy to get subtly wrong and every mistake is a security hole. Then the ZipProvider (#64915) and native addons from a mount (#65680). Then --vfs-load (#65748), the keystone: node --vfs-load=app.nzip runs the app inside. The bottom line is why upstream mattered in practice: before 26.10, deploying this way meant a 30 to 90 minute source build of a patched Node on each server.

III · What had to exist first

Node runs archives. It doesn’t decide which.

In the runtime · the primitive

  • Mount a zip as a directory
  • Resolve and run modules from it
  • Load native addons from it

Slow to change, then permanent. Right for a primitive.

In userland · the policy

  • Signatures and their formats
  • Whom you trust, and for what
  • Names, updates, warnings

Has to keep up with attackers, so it has to stay replaceable.

The design rule behind everything: standardise the primitive, never the policy. It's the lesson from about ten years on Temporal: the language got instants and calendars, not your business rules about working days. Here, the primitive is "an application can be loaded and run out of an archive", and that belongs in Node. Whether you should trust this particular archive must not be in Node: getting a signature format into the runtime takes two years, and getting it out again takes ten. So the trust layer, the bundle tool, is an ordinary npm package you can replace.

III · What had to exist first

Signing, with no key to lose

1 · observe

Run the app once and write down every file it reads.

2 · create

Archive exactly those files. Same files, same bytes.

3 · audit

Review it against the last release: you, or Claude in CI.

4 · sign

Only if the review came back clean.

# release.yml
permissions:
  id-token: write # that’s the key

Sigstore signs as your CI workflow, or as your browser sign-in on a laptop.

Users can require exactly that workflow, on main.

The second prerequisite: signing that doesn't mean managing keys. Sigstore issues a short-lived certificate for an identity you already have: your GitHub Actions workflow in CI, a browser login on your laptop. Nothing to store, nothing to leak. And signing is its own step, after an audit: observe, create, audit, sign. Recording beats static analysis because it catches dynamic requires and data files; the unused module in your source simply isn't in the archive. Archives are reproducible: the same files make the same bytes. bundle's own releases go through exactly this, with the audit done by Claude against the previous release.

III · What had to exist first

Names and vouching, with no new registry

publisher

Listing

“mdview is at this URL.” Releases stay where they are.

curator

Suite

“These go together, and each must carry this.”

auditor · scanner · IT

Attestation

“Audited”, “permitted”, “malware”, about one file’s hash.

Each one is a record in their own Atmosphere account, any provider.

Checked against the owner’s key with nothing but node:crypto.

You hold the policy: whose word counts, and whose warning stops an install.

An open index only says whom to ask.

The third prerequisite, and the one people don't expect: accounts that already exist. If you have an Atmosphere account, from whichever provider, you already have a place to publish signed records that anyone can verify without trusting the server. Every role writes only to its own account: the publisher says where the file is, the curator says what goes together, the auditor or scanner or your IT department says what they think of a file. A backlink index (Constellation) helps find records, but every record is fetched from its owner and checked against their key. Nobody runs a registry, so there's nothing in the middle to compromise. You don't need an account to install; only to publish names or attestations.

IV · What you can do now

Your app, one file, run by name

$ bundle create --base ./app -f app.manifest --launcher -o greet.unsigned.nzip
* unsigned archive (3 members, sha256 digests)
$ bundle sign greet.unsigned.nzip
* wrote greet.nzip (1904 bytes)
$ ./greet.nzip Grace
hello, Grace
$ head -2 greet.nzip
#!/bin/sh
exec node --no-warnings --experimental-vfs --vfs-load="$0" -- "$@"

Two kilobytes

Only the files the app read.

It’s a zip

unzip -l shows everything in it.

Plain node runs it

No node_modules, no install step.

Demo, or show the slide if the network is bad. The app was recorded first (the observe step), so the archive holds exactly the three files it read, and the unused module in the source isn't there. --launcher puts a two-line shell script in front of the zip, so the file runs by name. The signature covers the whole file, launcher included. That's wishes one and two from the list: one file, decided at release, runs by name. On Windows, bundle install sets up a .nzip file association so the same file runs by name there too.

IV · What you can do now

Install a stranger’s tool, and see who vouches for it.

$ bundle install @alice.example/tool
* tool: sha256:3f1a… (signed)
   1 signed by   …/acme/tool/.github/workflows/release.yml@refs/heads/main — new
   2 attested by audit.acme.com as audited — trusted by policy
     WARNING     scanner.example as malware — marked it bad
* accept which? numbers (1,2), 'all', or Enter to decline:

Nothing runs to install

Fetch, check, move into place. No install scripts.

You decide once

Your answer is remembered for every update.

Name it any way

A URL, a domain, or a name someone published.

Think of it as curl-pipe-sh with the two scary parts removed: nothing runs to install it, and nothing lands on disk unless it checks out. A file that doesn't match its signature is refused outright, so a tampered download never lands. Walk the prompt: a signer you haven't seen before is a question; an auditor your policy trusts goes straight through; a warning from a stranger is shown, not obeyed, because anyone can publish one, while a warning from someone you listed refuses it outright. Three ways to name an app: a URL, a domain whose TXT record says where, or a published name like this one. Next slide: the same install, without a terminal.

IV · What you can do now

One click on a link installs it.

on your page, README or post

<a href="nzip:alice.example/devtools">
  Install devtools
</a>

🌳 Install devtools

→

bundle opens a window with the same review and the same questions.

No terminal needed

Once bundle is installed, the browser hands nzip: links to it.

Names, never downloads

A link names something published. A page can’t point bundle at any old file.

Apps, suites, plugins

A plugin’s link installs it into its app. publish prints the link.

This is the one people underestimate. Once bundle is installed, it registers itself for nzip: links on Linux, macOS and Windows. An author puts a link on their page, their README, or in a chat message or a post; clicking it, the browser asks whether to open bundle, and bundle runs the same install as the terminal command, with the decisions in a window. So your designer, your PM, or the colleague who never opens a terminal can install your team's tools, and they still see who vouches for them. Safety: a link only ever names something published, an @handle/name or an at:// address, never a URL or a domain, so a web page can't make bundle fetch an arbitrary file. What it names is fetched, checked and reviewed like any install. bundle publish and bundle suite publish print the link for you, and the project's page lists every published app with its link. If links ever stop opening bundle, bundle links puts it right.

IV · What you can do now

Updates follow the publisher. Bad news finds you.

$ bundle update
1 of 4 updated: tool

# a new terminal, the next morning:
tool: WARNING — scanner.example as malware has marked it bad since it was last checked

$ bundle installed tool
tool CHANGED the file is not the bytes that were installed

Releases move, you follow

An install remembers how it was named, and asks again.

A quiet daily check

At shell start, and silent when there’s nothing to say.

Changes get noticed

Whoever touched the file on disk.

The part I like most: if a scanner flags something you installed last week, your next terminal tells you. You didn't subscribe to a mailing list or read a security advisory; the warning travelled to you, because it's an attestation about the exact hash you have. The shell check runs at most once a day, gives up quickly offline, and says nothing when there's nothing to say. bundle installed answers "is this still what I installed?" on any machine.

IV · What you can do now

Your team’s toolset, with one question

$ bundle install @acme.com/devtools
* suite devtools expects its members to carry:
   1 signed by …/acme/cli/…/release.yml@refs/heads/main — for cli
   2 attested by published@did:plc:… — for cli-git, cli-k8s
accept which, for those members? all
suite devtools: 3 installed

# and IT pushes one rule to every laptop:
{ "require": { "attesters": ["permitted@did:web:it.acme.com"] } }

Asked once

Every tool is still reviewed on its own.

Kept in step

Tools added are installed, tools dropped are removed.

IT can say yes or no

Permit the suite, prohibit one tool in it.

Back to the ten laptops. A suite is a list of things that go together, like your team's toolset, published by whoever curates it. It doesn't vouch for anything itself: it says what each tool must carry, so you're asked once instead of ten times. bundle update keeps everyone on the same set. The company case: IT requires "permitted by us" of everything, permits a whole suite with one attestation, and can still prohibit one tool inside it. That's wish six: the same thing on every laptop and in CI.

IV · Back on the server

Deploying a web service, now

# /etc/bundle/policy.json
{ "require": { "attesters":
  ["published@did:plc:…"] } }

$ bundle install --system \
    --name shop \
    @you.example/shop

# each systemd unit:
node --experimental-vfs \
  --vfs-load=…/shop.nzip -- run checkout

One app, every service a part

API, auth, workers, mail… each pinned by hash.

CI vouches for one hash

The servers only accept what that account attested.

Unchanged means untouched

Same bytes, same hash: not fetched, not restarted.

All or none

No half the services on last week’s release.

What’s on the server? One hash, and who vouched for it.

This closes the loop from the first slide. Picture a product made of many services. CI builds each service as a part, builds one app that pins every part's hash, and attests that one hash from its own Atmosphere account. The servers' policy only accepts that attestation, and it names a DID, never a handle, because handles change hands. Each systemd unit runs stock Node with the app and asks it to run one part; no unit points at a service's own archive. Archive members all carry a fixed date, so an unchanged part is the same bytes in the next release, keeps its hash, and its service isn't even restarted. Compare that with the deploy on slide two: no registry, no npm install, no copying files around, and a single answer to "what's running".

V · Why it matters

Why you, a JavaScript developer, should care

You can say what’s running

With a hash, on any server or laptop, months later.

You can share a tool

One file, one click, kept current. No support channel.

You choose whom to trust

See who vouches, and let your policy decide.

Built on Node itself: no new runtime, no new registry, no fork. You still develop with npm; this changes what you hand over.

Three takeaways, one per card; this is the slide people should remember. First, the question from the opening has an answer now. Second, sharing tooling stops being a support burden. Third, trust stops being an assumption you make about the registry and becomes something visible that you decide. And it doesn't ask you to switch runtimes or registries: it builds on features that are now in Node, and it doesn't replace npm; it's a way to ship what npm built.

V · Honestly

What this isn’t, yet

Not stable

Node 26.11+ with --experimental-vfs. Both sides are experimental.

Not a sandbox

Checked code runs with full access, like any Node program.

Not proof of safety

A signature says who built it. Review and attestations say the rest.

Not a replacement for npm

You still develop with npm. This changes what you hand over.

Before anyone goes and uses this for everything: four things it isn't. Being upfront here is what makes the rest credible. On "not proof of safety": most npm compromises shipped perfectly signed packages from real, hijacked accounts, which is exactly why attestations from other people exist.
