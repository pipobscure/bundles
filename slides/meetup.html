Show of hands

How do you ship a Node tool to someone?

npm install -g your-tool

Their machine resolves your dependency ranges against the registry, today, and runs install scripts while it does.

A Docker image

Works. Ships an operating system to run one command-line tool.

git clone && npm ci

A README full of steps, and a support channel for when step four fails.

"Compile it to a binary"

One file, but an opaque one, often built for a different runtime, and you trust it whole.

Every one of these works. None of them tells the person on the other end what they actually got.

the options you already know

"Hands up if you've published a CLI to npm. Keep it up if you've had a bug report that turned out to be someone's install, not your code."

50 seconds. Don't trash any option: they all work, and the audience uses them. The point is the last line: none of them answers "what did I just get?".

If someone shouts "bun build --compile" or "Node SEA": good, that's the fourth card. Come back to it on the comparison slide.

The awkward question

What is actually running on that machine?

  • Decided at install time, not when you released. ^1.2.0 means "whatever the registry says today".
  • Install runs code. postinstall scripts run before anyone has looked at anything.
  • Nothing records it. Two installs of the same version can differ, and nobody can tell you how.
  • And it gets attacked. Hijacked maintainer accounts and self-spreading install-script worms were both npm news in 2025.
$ npm install -g some-tool added 214 packages in 9s # which 214? from where? # what ran just now?

You shipped a version. They got whatever resolved.

version ≠ code

"When you publish version 1.4, you think you shipped 1.4. What you actually shipped is a recipe, and the user's machine cooks it."

60 seconds. Keep the supply-chain line short and factual. Don't name incidents unless you've checked the details recently; "hijacked accounts and install-script worms, both in 2025" is enough for this room and true.

The 214 packages line gets a laugh because everyone has seen it.

The idea

Freeze the whole tree into one file. Sign it. Let Node run it straight out of the file.

your app + node_modules

Exactly the files it reads. Nothing more.

one signed file

Decided once, when you release. Can't change afterwards.

plain node runs it

No install step, no registry, no extraction to disk.

@pipobscure/bundle

"So: don't ship the recipe. Ship the meal. One file, decided when you release it, signed, and Node runs it as it is."

45 seconds. This is the thesis. Everything after is "does it work" and "what does that get me".

The only internals slide

It's a zip.

$ unzip -Z1 greet.nzip index.js lib/hello.js package.json AUTHORITY.PEM # who signed it
  • A real ZIP. Every tool you have can open it. Nothing hidden.
  • One signature over the whole file. Change one byte, anywhere, and it no longer checks out.
  • Node runs it as a file system. Since Node 26, node --vfs-load=app.nzip mounts a zip and runs the app inside, no extracting.
that's all the format you need tonight

"That's as deep as we're going into the format. It's a zip, it's signed as a whole, and Node can run straight out of it now."

40 seconds. If anyone wants the byte layout, there's a whole other talk (Ship the Tree, same repo) and docs/design.md. Don't get pulled in here.

The Node piece, if asked: --vfs-load landed in 26.10, and the last piece for standalone executables in 26.11. Still behind --experimental-vfs.

Getting the tool

One command.

$ npx @pipobscure/bundle install * installing this package itself from https://github.com/pipobscure/bundles/releases/latest/download/bundle.nzip bundle installed in ~/.local/bin * add Tab completion, and a quiet daily re-check of what you install, to ~/.zshrc? [Y/n]

And the thing it installed is itself a bundle: one signed file, checked before it lands on your PATH.

npx @pipobscure/bundle install

"Getting the tool is the tool demonstrating itself: npm fetches it once, it verifies its own release, and puts one signed file on your PATH."

30 seconds. Have it installed already; don't run this live unless the network is good.

Demo 1

Pack it, sign it, run it.

# 1. run it once, and write down what it reads $ BUNDLE_MANIFEST=app.manifest node --experimental-vfs \ -r @pipobscure/bundle/record --vfs-load=./app -- Ada hello, Ada $ cat app.manifest package.json index.js lib/hello.js # lib/never-used.js? not read, not in
# 2. pack exactly that $ bundle create --base ./app -f app.manifest -o greet.run * unsigned archive (3 members, sha256 digests)
# 3. sign it $ bundle sign --launcher -o greet.nzip greet.run * signed: 5e8e6ade4ec94378ead2… * wrote greet.nzip (1904 bytes)
# 4. it's a program $ ./greet.nzip Grace hello, Grace $ head -2 greet.nzip #!/bin/sh exec node --no-warnings --experimental-vfs --vfs-load="$0" -- "$@"

Two kilobytes. No node_modules on the other end, no install step.

observe → create → sign → run

Beat 1, observe (40s). "Static analysis gets dynamic requires and data files wrong. So we don't analyse, we run it and write down what it opened." Point at lib/never-used.js: in the source, not in the bundle, because nothing read it.

Beat 2, create (20s). Fast. The .run extension means unsigned.

Beat 3, sign (30s). "By default this signs with sigstore: your GitHub Actions identity in CI, a browser login on your laptop. No key file to keep or leak." Live, sign with whatever you rehearsed with; the output shape is the same.

Beat 4, run (40s). The beat people react to. Show the first two lines: it's a two-line shell script, then a zip. Node mounts the file and runs the app inside it.

Fallback: the artifacts from rehearsal are in the demo folder. Run ./greet.nzip Grace and move on; never debug on stage.

Demo 2

Now break it.

# change one byte in the middle $ cp greet.nzip evil.nzip $ printf X | dd of=evil.nzip bs=1 seek=300 conv=notrunc $ bundle verify evil.nzip INVALID — archive hash does not match the recorded hash $ bundle run evil.nzip Grace error: refusing to run 'evil.nzip': invalid — archive hash does not match the recorded hash
$ bundle verify greet.nzip VALID — trusted certificate chain

The honest part

  • ./evil.nzip still runs. A #! line can't check anything; it just starts Node.
  • bundle run checks before a single line of the app runs, and keeps checking every file as it's read.
  • A standalone executable checks itself. That's the next demo.
one byte → refused

"One byte. Not the code, not a file inside: one byte anywhere in the file."

Say the honest part out loud (30s). Running the tampered file by name still runs it. A shebang script has no way to check anything, and the tool says so rather than pretending. If you want the check, run it through bundle run, or ship the standalone executable on the next slide, which can't skip it.

This candour earns trust for the rest of the talk. Don't rush it.

Demo 3

No Node on the other end?

$ bundle sea --output greet greet.run * building the SEA base (node runtime + verifier) * appending greet.run behind sea-base * wrote greet $ ./greet Grace hello, Grace # the same byte flip, inside the executable: $ ./greet-tampered Grace refusing to run: … invalid
  • One executable: Node, the verifier, and your app, signed as a whole.
  • It checks itself before running anything, every time. There's no way to start it that skips the check.
  • It can carry its own rules, such as "only run if signed by our release workflow".
  • Worker threads just work, and they're checked too.
bundle sea

"Same app, same build, but now Node itself is inside the file, and the file refuses to run if it's been touched."

Honest number if asked: it's a copy of Node, so it's about 155 MB. The trade-off is "nothing to install".

Windows: the executable gets .exe and runs the same way. The shell-launcher version uses a file association on Windows that bundle install sets up.

Fallback: building the base takes a few seconds. Pre-build it before the talk and pass --base.

Does it actually work?

The tool ships this way.

npm's bundle is a .nzip

The package's command is the signed file itself. No wrapper script in between.

Released by CI

Tested on Linux and Windows, audited, signed with the workflow's own identity, published. No secrets.

Checkable by anyone

unzip -l shows what's in it. bundle verify shows who signed it.

eating our own cooking

"The best evidence that this works is that the tool itself is shipped this way, release after release, from CI."

45 seconds. No secrets in CI: npm trusted publishing and sigstore both use the GitHub Actions identity token.

Installing other people's apps

See who vouches, then decide.

$ bundle install @alice.example/tool # or a URL, or a domain * tool: sha256:3f1a… (signed) 1 signed by https://github.com/acme/tool/.github/workflows/release.yml@refs/heads/main — new 2 attested by audit.acme.com (did:web:audit.acme.com) as audited — trusted by policy WARNING scanner.example (did:plc:…) as malware — marked it bad * tool: … accept which? numbers (1,2), 'all', or Enter to decline:
  • Nothing runs to install it. Fetch, check, move into place. No install scripts.
  • You decide whom to trust, once. Your answer is remembered for every update.
  • Broken or tampered files never land. Not even briefly.
curl | sh, minus the scary parts

"Think of it as curl-pipe-sh with the two scary parts removed: nothing runs to install it, and nothing lands on disk unless it checks out."

Walk the prompt (40s): a signer you haven't seen before is a question. An auditor your policy trusts goes straight through. A warning from a stranger is shown, not obeyed, because anyone can publish one. A warning from someone you block on refuses it outright.

Three ways to name an app: a URL, a domain (a TXT record says where), or a published name, which is the next slide.

After the install

Stay current, hear about problems.

$ bundle update 1 of 4 updated: tool # a new terminal, the next morning: tool: WARNING — scanner.example (did:plc:…) as malware has marked it bad since it was last checked $ bundle installed tool CHANGED the file is not the bytes that were installed
  • Updates follow the publisher. Moved releases, a new URL, a renamed domain: update finds them.
  • Bad news finds you. A quiet check at shell start tells you when someone flags something you installed.
  • Changed files get noticed, whoever changed them.
update · validate · installed

"The part I like most: if a scanner flags something you installed last week, your next terminal tells you."

60 seconds. The shell check runs at most once a day, gives up quickly offline, and says nothing when there's nothing to say.

Publishing, without a registry

Your Bluesky handle is your publisher name.

$ bundle publish --as you.example --description 'preview markdown in the terminal' \ mdview https://github.com/you/mdview/releases/latest/download/mdview.nzip published mdview as did:plc:… # anyone, anywhere: $ bundle search markdown @you.example/mdview preview markdown in the terminal $ bundle install @you.example/mdview

A record in your account

atproto, the protocol behind Bluesky. It points at your release URL.

Releases stay releases

A new version is a new GitHub release. The listing never changes.

No registry to run

Nothing new to compromise. Search runs against a local index.

publish · search · install @you/name

"There's no new registry here. If you have a Bluesky account, you already have a place to publish: the listing lives in your own account and says where the file is."

If asked "why atproto?": accounts that already exist, records anyone can verify without trusting the server, and an open index (Constellation) that lets everyone find listings. A domain with a TXT record works too, for people who'd rather not.

Trust, made visible

Who vouches for this file?

The signature

Who built it. With sigstore that's your CI workflow or your login. No keys to manage.

Attestations

Anyone can vouch for a file ("audited", "rebuilt it, same bytes") or warn against it, from their own account.

Your policy

Whom you trust, what you require, whose warnings stop an install.

$ bundle attest --as audit.acme.com --kind audited tool.nzip # vouch $ bundle attest --as scanner.example --verdict bad --kind malware tool.nzip # warn
signatures · attestations · policy

"A signature tells you who built it. It doesn't tell you it's safe: most npm compromises shipped perfectly signed packages from real, hijacked accounts. So other people get to say things about the file too."

70 seconds. Attestations are one record per file in the attester's own account. Withdrawing is deleting the record. Checking them works offline from a cache.

For app authors

Plugins that are signed bundles too.

// in your app import { use, list } from '@pipobscure/bundle/plugins'; use('bled'); // this app's plugins const gpio = await import('@alice/bled-gpio'); // plain import // and, if you want, checked as they load: use('bled', { verify: { attesters: ['audited@did:web:bled.dev'] } });
# for your users $ bundle search --for bled gpio $ bundle install --for bled @alice.example/bled-gpio
  • Ordinary import and require. Your plugin code doesn't change.
  • A plugin can't replace your dependencies. Yours always win; plugins only fill gaps.
  • Plugins get your app's modules, the same instance your app has.
  • Installed per app, reviewed like any install, removed with the app.
use() · install --for · search --for

"If your app takes plugins today, they're probably npm packages in node_modules. Same code, but now they're signed files, installed for your app, and you can require that they're audited."

Key safety property (say it): plugins resolve last. A plugin called lodash can't swap out your lodash.

Judged as plugins: your app's signing rules don't apply to plugins, because someone else wrote them. Attestation rules do. Don't go deeper unless asked.

In your pipeline

Release from CI, with no secrets.

# .github/workflows/release.yml (the gist) permissions: id-token: write # sigstore signs as this workflow contents: write steps: - run: npm ci - run: npx bundle create --base . --files app.manifest --output app.run - run: npx bundle audit --check app.run # the gate - run: npx bundle sign --launcher --output app.nzip app.run - run: gh release upload "$TAG" app.nzip

No key to store

The workflow's own identity signs, and users can require exactly that workflow.

A gate you choose

audit --check refuses unless a clean verdict covers these exact bytes.

Reviewed by Claude, or you

bundle skill installs the review procedure.

create → audit → sign → release

"In CI the signer is the workflow itself, so there's nothing to leak, and your users can say 'only accept it if it was signed by that workflow on main'."

Honestly

What this is not.

  • Not stable yet. It needs Node 26.11+ with --experimental-vfs, and both sides are experimental.
  • Not a sandbox. Checked code runs with full access to your machine, like any Node program.
  • Not proof of safety. A signature says who built it, not that it's harmless. That's what review and attestations are for.
  • Not checked when run by name. Use bundle run or a standalone executable when you want the check every time.
experimental, and saying so

"Before you go and use this for everything: four things it isn't."

50 seconds. Being upfront here is what makes the rest credible.

github.com/pipobscure/bundles

Likely questions, short answers:

  • "Native addons?" Yes. Node loads them straight out of the archive.
  • "How big is a bundle?" Only the files the app read. A small CLI is kilobytes. The standalone executable is a copy of Node, about 155 MB.
  • "Do I need Bluesky?" No. Install by URL or domain, sign with sigstore or your own CA. Accounts are only for publishing names and attestations.
  • "Windows?" Yes, tested in CI. bundle install sets up a .nzip file association so apps run by name.
  • "Isn't npm provenance enough?" It's good, and it's about packages you're about to install from npm. This is about the finished app you hand over.
  • "Reproducible builds?" Complementary. A "reproduced" attestation is someone saying "I rebuilt it and got these exact bytes".
  • "Bun or Deno?" This builds on Node's own new features, so it's Node.
